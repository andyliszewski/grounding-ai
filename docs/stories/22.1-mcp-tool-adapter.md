# Story 22.1: MCP Stdio Bridge + Registry Integration

**Epic:** Epic 22 — MCP Tool Bridge
**Status:** Draft
**Owner:** Product Owner (Sarah)
**Created:** 2026-04-25
**Dependencies:** Epic 12 (Agentic Tool Calling — provides `ToolRegistry` and `run_agentic_loop`)
**Coordinates with:** Epic 21 (Agentic-Mode Safeguards — forward-compat on `category` arg)

---

## Story

**As a** maintainer running `local_rag.py --agentic`,
**I want** a configurable bridge that spawns external MCP servers as subprocesses and registers their tools into the agentic loop's `ToolRegistry`,
**so that** any MCP server I already use elsewhere (webcrawl-mcp, future Gmail/Calendar/etc.) becomes callable by the local LLM with no per-server Python glue in this repo.

---

## Background

Today the agentic loop is closed-world. `scripts/local_rag.py:458-473`
registers exactly the tools whose code lives in this repo:
`search_corpus` plus the filesystem suite (`bash`, `read_file`,
`write_file`, `edit_file`, `glob`, `grep`, `notebook_edit`). External
MCP servers — even ones I built myself like `webcrawl-mcp` — are
invisible to the local LLM in `--agentic` mode.

Two paths to fix it were considered (Epic 22 Overview): a direct Python
wrapper for webcrawl-mcp specifically (~30 lines, single-purpose), or a
generic MCP bridge (~150 lines, reusable for every future MCP server).
The generic bridge is the chosen path. **This story ships the bridge
itself — not the webcrawl-mcp registration**, which is 22.2. The
deliverable here is an abstraction proven against an MCP server that
already lives in this repo: `mcp_servers/corpus_search/server.py`.

That in-repo server is a happy accident: it's a real MCP server, it
already works, it has zero external dependencies, and CI can spawn it.
It's a perfect fixture for testing the bridge without depending on
webcrawl-mcp being installed in the CI environment.

The bridge speaks MCP's stdio JSON-RPC dialect using only Python stdlib
(`subprocess`, `json`, `threading`, `queue`). No new pip dependency.
The MCP message format is well-specified for stdio transport; we don't
need the full `mcp` SDK on the client side for what this epic covers.

This story does **not** integrate with Epic 21's `PermissionBroker`
(it's still in Draft). Instead, it establishes a forward-compat hook:
`MCPServerSpec` carries a `category` field and an optional
`tool_categories` per-tool override. Until 21.1 lands, those values are
stored on a side-channel attribute (`registry._tool_categories`) and
unused. When 21.1 ships, swapping to the real `category=` arg in
`ToolRegistry.register` is a one-line change called out in Story 22.3.

## Acceptance Criteria

1. **New module `scripts/mcp_tool_adapter.py`** exports the following
   public surface (signatures are guidance — refine in implementation if
   the JSON-RPC plumbing demands):

   ```python
   @dataclass
   class MCPServerSpec:
       name: str
       command: list[str]
       env: dict[str, str] = field(default_factory=dict)
       cwd: Optional[Path] = None
       timeout_s: float = 30.0
       startup_timeout_s: float = 10.0
       category: str = "network"
       tool_categories: dict[str, str] = field(default_factory=dict)
       max_response_bytes: int = 50 * 1024
       # name defaults to command[0]'s basename if blank

   class MCPClient:
       def __init__(self, spec: MCPServerSpec): ...
       def start(self) -> list[dict]: ...      # returns tools/list response
       def call_tool(self, name: str, arguments: dict) -> str: ...
       def stop(self, timeout_s: float = 5.0) -> None: ...
       @property
       def alive(self) -> bool: ...

   def register_mcp_tools(
       registry: "ToolRegistry",
       specs: list[MCPServerSpec],
       *,
       on_collision: Literal["namespace", "skip", "error"] = "namespace",
   ) -> list[MCPClient]: ...

   def load_mcp_specs_from_config(
       config_path: Optional[Path] = None,
       cli_overrides: Optional[list[str]] = None,
   ) -> list[MCPServerSpec]: ...
   ```

2. **Stdio JSON-RPC handshake.** `MCPClient.start()`:
   - Spawns the subprocess with `subprocess.Popen`, `stdin=PIPE`,
     `stdout=PIPE`, `stderr=PIPE` (stderr captured for error logging
     but otherwise drained on a background thread to prevent buffer
     deadlock).
   - Sends `initialize` JSON-RPC request with `protocolVersion`
     advertised at the spec rev current at story-implementation time
     (write the rev as a module-level constant; document in the
     module docstring).
   - Sends `notifications/initialized` after receiving the
     initialize response.
   - Sends `tools/list` and returns the response.
   - Times out at `spec.startup_timeout_s` for the full handshake.
     On timeout, terminates the subprocess and raises a clear
     exception naming the spec.

3. **Per-call dispatch.** `MCPClient.call_tool(name, arguments)`:
   - Sends `tools/call` JSON-RPC request with the tool name and
     arguments.
   - Awaits one matching response (matched on `id`, ignoring
     server-initiated notifications and unrelated responses).
   - Times out at `spec.timeout_s` per call. On timeout, returns the
     string `"<MCP timeout after Ns calling tool '{name}' on server '{spec.name}'>"`
     to the caller; subprocess remains alive for subsequent calls.
   - Stringifies the response `content` (MCP returns a list of
     content blocks with `type` and `text` / structured fields). For
     text blocks, concatenate `text` fields. For non-text blocks,
     emit a `<non-text content: {type}>` placeholder. Document the
     contract in the module docstring.
   - Truncates the final string at `spec.max_response_bytes` with a
     `\n<truncated, full size N bytes>` marker.

4. **Crash detection.** If the subprocess exits while `call_tool` is
   waiting on a response (poll detects exit), `call_tool` returns the
   string `"<MCP server '{spec.name}' exited unexpectedly (rc={rc})>"`
   and `MCPClient.alive` flips to `False`. Subsequent calls return the
   same error without retrying. No auto-restart in this story.

5. **Lifecycle: clean shutdown.**
   - `MCPClient.stop()` sends SIGTERM, waits up to `timeout_s`
     seconds, then SIGKILL. Joins the stderr-drain thread.
   - `register_mcp_tools` registers an `atexit` callback that calls
     `stop()` on every live client. Wires a `signal.signal(SIGINT, ...)`
     handler that triggers the same cleanup before re-raising. (The
     existing REPL Ctrl-C handling continues to work; this addition
     just ensures subprocesses are reaped first.)
   - On normal REPL exit (via `quit` command), no leaked subprocesses
     remain — verifiable via `ps` or `psutil.Process(...).children()`.

6. **Registration into `ToolRegistry`.** For each tool returned by
   `tools/list`:
   - Build a `(name, schema, executor)` triple where `schema` is
     converted from MCP's `inputSchema` format to OpenAI tool-schema
     format (the existing dialect `ToolRegistry` consumes). The
     conversion is the obvious nested rename:
     `{"name": ..., "description": ..., "inputSchema": {...}}` →
     `{"type": "function", "function": {"name": ..., "description": ..., "parameters": {...}}}`.
   - The `executor` is a closure capturing `(client, tool_name)` that
     calls `client.call_tool(tool_name, arguments)`.
   - Apply collision policy (AC 7) before calling
     `registry.register(name, schema, executor)`.

7. **Tool-name collision policy.** Implementation of the
   `on_collision` parameter:
   - `"namespace"` (default for `local_rag.py` integration): if `name`
     is already in `registry.tool_names`, register as
     `f"{spec.name}__{name}"` and emit a WARNING log line:
     `"MCP tool name collision: '<name>' from server '<spec.name>' registered as '<spec.name>__<name>' (in-repo or earlier MCP tool wins)"`.
   - `"skip"`: if collision, drop the tool with a WARNING log and
     don't register it.
   - `"error"`: if collision, raise `MCPToolCollisionError` (new
     exception in the module). Useful for tests; not the runtime
     default.
   - Collisions between two MCP servers follow the same policy: first
     registered wins under the bare name, subsequent get namespaced.

8. **Forward-compat with Epic 21 `category` arg.** `ToolRegistry.register`
   does not yet accept `category` (Story 21.1 will add it). Until then,
   `register_mcp_tools` writes per-tool category metadata to a
   side-channel attribute on the registry:
   ```python
   if not hasattr(registry, "_tool_categories"):
       registry._tool_categories = {}
   registry._tool_categories[final_name] = (
       spec.tool_categories.get(name, spec.category)
   )
   ```
   When 21.1 lands, this code is replaced in 22.3 with a real
   `category=` kwarg. This story does not enforce categories; it only
   stores them.

9. **Config loader: `load_mcp_specs_from_config`** reads from:
   - `config_path` if provided, else the existing `config.yaml` resolution
     used by `RerankConfig` / `HybridConfig` (see
     `scripts/local_rag.py` arg parsing for the `--config` flag and
     `grounding/config.py` if a shared loader exists; otherwise
     fall back to a stdlib YAML read).
   - The top-level `mcp_servers:` block (a list of dicts).
   - `cli_overrides`: a list of strings, each interpreted as either an
     absolute path to an MCP server executable (treated as a `command`
     with no env, default name = basename) or a `name=command` form.
     CLI overrides **append** to (not replace) the config block.
   - Returns `[]` when no config and no overrides — the no-op happy path.
   - Raises a clear exception (with the file path and line if
     possible) on malformed config. Same posture as Epic 21's
     malformed-config rejection: opt-in features fail loud, not silent.

10. **`local_rag.py` integration.** The agentic-setup block at
    `scripts/local_rag.py:458-473` grows two new lines:

    ```python
    mcp_specs = load_mcp_specs_from_config(args.config, args.mcp_server)
    mcp_clients = register_mcp_tools(registry, mcp_specs)
    ```

    Two new CLI flags:
    - `--mcp-server SPEC` — repeatable; appends to the config-loaded
      list. Each `SPEC` is either an absolute path or `name=path`.
    - `--mcp-servers-config PATH` — alternative config file path
      (defers to `--config` if both provided, with a documented
      precedence: `--mcp-servers-config` wins for the `mcp_servers:`
      block specifically; `--config` continues to win for everything
      else).
    The two flags are mutually informative: most users will set the
    block in `config.yaml` and not need either flag.

11. **Behavior unchanged when `mcp_servers:` is absent or empty.** A
    fresh clone with no `mcp_servers:` block runs `local_rag.py
    --agentic` with byte-identical behavior to pre-22.1 — same tool
    list, same prompt, same outputs. Verifiable by diffing a verbose
    trace before and after the change with no config block.

12. **Unit tests in `tests/test_mcp_tool_adapter.py`** cover (using the
    in-repo `mcp_servers/corpus_search/server.py` as the live fixture):
    - `MCPServerSpec` defaults and validation.
    - `MCPClient.start` happy path against the corpus_search server:
      handshake completes, `tools/list` returns the `search_corpus`
      tool with its expected schema fields.
    - `MCPClient.start` failure: bad command (executable not found)
      raises a clear exception within `startup_timeout_s`.
    - `MCPClient.call_tool` happy path: round-trips a `search_corpus`
      call and returns a string. (Fixture: a tiny test corpus or the
      mini fixture corpus already used in
      `tests/eval_fixtures/mini_corpus/`.)
    - `MCPClient.call_tool` timeout: a deliberately slow tool (mock
      server with `time.sleep`) returns the timeout error string
      within `timeout_s` ± slack.
    - `MCPClient` crash mid-call: SIGKILL the subprocess from the
      test, assert the in-flight `call_tool` returns the
      "exited unexpectedly" string and `client.alive` is `False`.
    - `MCPClient.stop`: terminates cleanly; no zombie subprocess after
      `wait()`.
    - `register_mcp_tools` with empty list is a no-op (registry
      unchanged).
    - `register_mcp_tools` with one server registers each tool
      returned by `tools/list`.
    - Collision policy: register a tool with a name already in the
      registry; assert namespaced name + WARNING log; switch policy
      to `"skip"` and `"error"` and assert each behavior.
    - `load_mcp_specs_from_config` with no `mcp_servers:` block
      returns `[]`.
    - `load_mcp_specs_from_config` with a valid block parses to
      `MCPServerSpec` instances with all fields populated.
    - `load_mcp_specs_from_config` with malformed block raises a
      clear exception naming the file.
    - CLI override append semantics (string parsed correctly, both
      bare-path and `name=path` forms).

13. **One integration test in `tests/test_mcp_tool_adapter.py`**
    constructs a real `ToolRegistry`, calls
    `register_mcp_tools(registry, [corpus_search_spec])`, asserts the
    `search_corpus` tool is registered, then calls
    `registry.execute("search_corpus", {...})` and asserts the result
    is a non-empty string. No Ollama, no LLM — exercises only the
    registration + dispatch path. Cleanup invokes `stop()` on every
    client, asserts no leaked subprocesses (via `psutil` if available,
    otherwise via `MCPClient.alive` checks).

14. **No new pip dependencies.** The bridge uses stdlib only. If
    `psutil` is needed for the integration-test cleanup assertion,
    add it as a dev-only dep (`pyproject.toml` `[project.optional-dependencies]
    dev`), not a runtime dep.

15. **`scripts/mcp_tool_adapter.py` module docstring** documents:
    - The MCP spec rev being targeted (with link).
    - The OpenAI ↔ MCP schema conversion contract.
    - The collision policy with the `local_rag.py` default.
    - The forward-compat plan for Epic 21.
    - That HTTP/SSE transport is out of scope (stdio only).

16. **Observability.** `register_mcp_tools` logs at INFO level for each
    successfully registered server: `"Registered MCP server '<name>': N

    collisions per AC 7. Verbose (`-v`) is unchanged — these are
    standard logger lines, not REPL output.

## Dev Notes

### Why we don't use the official `mcp` Python SDK on the client side

The MCP SDK provides client classes that handle stdio JSON-RPC, but
adopting it would add `mcp>=1.0.0` as a runtime pip dep, plus its
transitive dependencies (which include `pydantic`). This story does
the stdio handshake and one request/response shape (`tools/call`)
hand-rolled in ~150 lines of stdlib. The benefit:
- Zero new runtime deps (consistent with Epic 19's "no new heavy
  dependencies" principle).
- Forward-compat is easy: if MCP's stdio JSON-RPC shape evolves, we
  pin a spec rev and update the handful of constants.
- Tests can spawn the in-repo `corpus_search` server with no extra
  install.

If the bridge ever needs HTTP/SSE transport or richer features
(server-initiated notifications, sampling), revisit — at that point
the SDK pays for itself.

### Why the in-repo `corpus_search` server is the right test fixture

`mcp_servers/corpus_search/server.py` is already a working MCP server.
It runs over stdio. CI already has whatever it needs to run (it's
in the same Python project). Using it as the test fixture for the
bridge means:
- Tests don't need to install webcrawl-mcp.
- Tests exercise the full real protocol path, not a hand-rolled mock.
- A bug in the bridge that's specific to a real MCP server's behavior
  (e.g., FastMCP's exact `tools/list` response shape) gets caught in
  CI rather than discovered manually in 22.2.

The corpus_search server collides with the in-repo `search_corpus`
tool name — that's *also* a feature, not a bug. It exercises the
collision policy in a real configuration (Task 7's smoke test).

### Why category metadata is side-channel-attached, not stored in the schema

`ToolRegistry.register` accepts `(name, schema, executor)` only. We
could shoehorn `category` into the schema dict (a custom non-OpenAI
field), but then any schema validator downstream would either reject it
or silently consume it. Side-channel attachment via a dict on the
registry instance is ugly but explicit, and Story 22.3 will replace it
with a real arg as soon as 21.1 lands. The ugliness is bounded in time.

### Why `atexit` + signal handler instead of context-manager-only

`local_rag.py`'s REPL is a long-running interactive loop. There's no
single `with` scope to wrap. The user can:
- Type `quit` (clean exit; atexit fires).
- Hit Ctrl-C once during a query (REPL catches; atexit fires on
  eventual exit).
- Hit Ctrl-C twice or send SIGTERM (no clean shell exit; signal handler
  must reap).
- Crash the Python process (nothing we can do; subprocesses leak).

The atexit + SIGINT handler combo covers the first three. The fourth
is documented as a known limitation; users who need bulletproof reaping
can run the REPL under `setsid` or a process group manager.

### Why no auto-restart of crashed MCP servers

Auto-restart hides the underlying problem: if webcrawl-mcp crashes on
a query, the user wants to see that and investigate. Restarting silently
turns a crash into a slow degradation. Fail-fast with a clear "exited
unexpectedly" string in the LLM's tool-result history is the right
default; the LLM may even retry the call itself, which is observable
via the iteration count and verbose trace. Auto-restart is in the
"Future Enhancements" list for the epic if real-world use shows the
fail-fast posture is too brittle.

### Why HTTP/SSE transport is out of scope

Stdio is the universal MCP transport — every server supports it, every
client supports it, the JSON-RPC framing is trivial. HTTP/SSE adds
auth, connection management, retry policies, TLS, and a lot of surface
area for what is currently zero benefit (no remote MCP servers in the
user's environment). When a real consumer for HTTP-transport MCP
emerges, file a follow-up epic.

### Coordination with Epic 21 (forward-compat)

Epic 21 will add a `category` argument to `ToolRegistry.register`
(Story 21.1 AC 2). The migration story for 22 + 21 is:

1. **22 ships first (likely).** This story stores `category` on
   `registry._tool_categories` side-channel.
2. **21.1 ships.** `ToolRegistry.register(name, schema, executor,
   category=...)`. The in-repo `register` calls in
   `scripts/local_rag.py` and `create_all_filesystem_tools()` are
   updated to pass categories.
3. **22.3 picks it up.** `register_mcp_tools` switches from the
   side-channel write to passing `category=` directly. Side-channel
   attribute is removed. One PR, ~5 lines.

If Epic 21 ships first instead, this story implements the
side-channel-vs-real-arg switch on first build — no follow-up needed.
22.3's AC 2 will reflect whichever order actually happens.

### Coordination with my-agents repo

None. This story doesn't touch agent YAML files. The
`scripts/local_rag.py` integration adds CLI flags and registers MCP
tools alongside in-repo ones; agent personas continue to be loaded
unchanged from `agents/<name>.yaml` in the maintainer's `my-agents`
repo via the existing loader.

### Public-mirror coordination

This story ships entirely on public `main`. Single squashed PR.
Reviewers should check:

- The test suite passes without network access and without
  webcrawl-mcp installed.
- The verbose-trace diff for the no-MCP case is empty.
- The collision-policy WARNING fires when expected.
