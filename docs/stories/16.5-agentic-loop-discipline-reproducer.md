# Story 16.5: Agentic-Loop Discipline Reproducer Suite

**Epic:** Epic 16 - Retrieval Evaluation Harness
**Status:** Draft
**Owner:** Product Owner (Sarah)
**Created:** 2026-04-25
**Dependencies:** Epic 12 (Agentic Tool Calling), Epic 19 (Hybrid Retrieval — for confirming retrieval quality is not the issue)
**Related:** ROADMAP measurement-before-flip discipline (Epic 18.4 / 19.4 precedent)

---

## Story

**As a** grounding-ai maintainer,
**I want** a small, committed reproducer suite that measures whether local LLMs in `--agentic` mode synthesize from already-retrieved chunks or loop on reformulated queries,
**so that** any subsequent prompt-discipline fix (per-agent, MCP tool description, or mechanical guardrail) is grounded in data across multiple models and agents — not the single observation that motivated this work.

---

## Background

A single observation against the `coder` agent showed `qwen3.6:27b` looping for 5 iterations on a query whose answer chunk (Clean Code, "first rule of functions," chunk `e12239a3-0970`) was returned by FAISS+BM25 hybrid on iteration 1 with score 0.48. `qwen2.5:32b` answered the same query against the same corpus in 2 iterations.

Possible fix scopes range from per-agent prompt nudge to cross-cutting MCP tool-description change to mechanical guardrail in `scripts/agentic.py`. All carry tradeoffs that compound on every future query for every user. Per the discipline established in Stories 18.4 and 19.4 — measure before changing user-visible behavior — this story produces the data that gates the fix decision.

**This story produces data and a written recommendation, not code changes.** Any prompt change, MCP description edit, agent YAML edit, or `scripts/agentic.py` modification is explicitly out of scope. Those gate on this story's recommendation.

---

## Acceptance Criteria

1. A `scripts/eval/agentic_loop_discipline.py` runner exists that takes a query suite YAML, a list of `(model, agent)` cells, and emits a JSONL trace per (cell, query) plus a summary markdown report. The runner reuses `agentic.run_agentic_loop` from `scripts/agentic.py:288` — no parallel re-implementation of the loop.

2. A query suite is committed at `docs/eval/agentic_loop_discipline/queries.yaml` containing **8 queries per agent** for **2 agents** (coder + one of {scientist, philosopher} — maintainer chooses). Every query has the shape: *single canonical answer-bearing chunk in the agent's corpus, verified by manual inspection*. The Clean-Code "first rule of functions" query is item 1 for the coder agent. Each item records:
   - `id` (e.g., `coder-001`)
   - `query` (the user-facing question)
   - `expected_chunk_id` (the canonical chunk that should suffice)
   - `expected_keywords` (3–5 phrases that must appear in a correct answer; used as a coarse correctness pre-filter, not the final grade)
   - `notes` (why this chunk is canonical)

3. The matrix is **3 models × 2 agents × 8 queries = 48 runs**, with cells:
   - **`qwen3.6:27b`** — the model where looping was observed.
   - **`qwen2.5:32b`** — the model that answered correctly on the motivating query.
   - **One out-of-family control** — `gemma3:27b` or `llama4`-mid-size or similar; non-Qwen, modern, 25–35B size class. Maintainer picks one based on what's pullable on the run host. The runner records the exact tag used.
   Run host, Ollama version, and tag SHA are recorded in the report header.

4. Per-run measurements captured into JSONL (`docs/eval/agentic_loop_discipline/traces/<run_id>/<cell>-<query_id>.jsonl`):
   - `iterations` — count of LLM calls in the loop.
   - `tool_calls` — full list of `(name, arguments)` tuples.
   - `redundant_retrievals` — count of `search_corpus` calls whose top-1 chunk_id appears in any prior iteration's tool-result for this run. The looping indicator.
   - `expected_chunk_seen_at_iter` — first iteration whose `search_corpus` result includes `expected_chunk_id` (the test of "did retrieval ever surface the right chunk").
   - `final_answer` — the assistant's last text message.
   - `correct` — boolean, manually graded by the maintainer post-run via a CLI prompt the runner emits per cell. Pre-fill suggestion based on `expected_keywords` presence; maintainer confirms or overrides.
   - `wall_seconds` — total run time.
   - `stopped_reason` — from `AgentLoopResult` (`complete` / `max_iterations` / `error`).

5. Sampling: `temperature=0.2` and `max_iterations=5` for every cell. Single run per cell (N=1). Deviation from a cell's expected behavior at N=1 is the signal — tight statistics aren't the goal.

6. The summary report is committed at `docs/eval/agentic_loop_discipline/report-2026-04-XX.md` with:
   - Run host, date, Ollama version, tag SHAs for all three models, query suite version.
   - Per-cell aggregate table: `(model × agent) → {avg iterations, avg redundant retrievals, % correct, expected-chunk-surfaced rate, max-iter-hit count}`.
   - Per-query breakdown for any cell where the model did not answer correctly: query, iterations, tool-call sequence, why-it-failed annotation.
   - **Written recommendation section** with one of the following decisions:
     - **No fix.** Failure mode is `qwen3.6:27b`-only; document model-selection guidance in CLAUDE.md and close.
     - **Per-agent prompt nudge.** Failure mode varies by agent; recommend extending the existing `style:` field in agent YAML (no schema change) for affected agents only. Specify which agents.
     - **Cross-cutting nudge.** Failure mode is broad; recommend a follow-up epic to edit the MCP `search_corpus` tool description and/or `scripts/local_rag.py` system prompt.
     - **Mechanical guardrail.** Looping is widespread and prompt-only fixes are insufficient; recommend a follow-up epic to add a synthesis-now injector to `scripts/agentic.py`.

7. A separate `expected_chunk_seen_at_iter` track confirms retrieval quality is not the issue. If for any (model, query) cell the expected chunk is never surfaced in 5 iterations, that cell is flagged as **retrieval-bounded, not synthesis-bounded** and excluded from the synthesis-discipline conclusion.

8. The runner is reproducible: `python scripts/eval/agentic_loop_discipline.py --suite docs/eval/agentic_loop_discipline/queries.yaml --models qwen3.6:27b,qwen2.5:32b,gemma3:27b --agents coder,scientist --out docs/eval/agentic_loop_discipline/traces/<run_id>/` runs the full matrix and emits both JSONL traces and the summary markdown.

9. **Out of scope for this story (gated on the recommendation):**
   - Any change to `agents/<name>.yaml` files (lives in the separate `my-agents` repo).
   - Any change to `mcp_servers/corpus_search/server.py`.
   - Any change to `scripts/agentic.py` loop logic.
   - Any change to `scripts/local_rag.py` system prompt.
   - CI integration of this runner (one-shot research run, not a recurring measurement).
   - Statistical significance testing (N=1 per cell is intentional).

## Dev Notes

### Why a one-off script and not an extension to `grounding eval`

Epic 16's `grounding eval` measures **retrieval quality** (recall@k, MRR, nDCG over chunk sets). This story measures **agentic-loop runtime behavior** (iterations, synthesis-vs-loop). Different surfaces, different metrics. Folding this into `grounding/eval/` now would couple measurement-of-retrieval to measurement-of-LLM-behavior at a point where the LLM-behavior methodology is unproven. If the methodology proves out — i.e., the recommendation justifies a fix and the runner survives review — promoting the script into `grounding/eval/agentic.py` is a reasonable follow-up. Until then, keep it as a standalone reproducer.

### Why N=1 per cell

The signal we're looking for is qualitative: does the model loop on this query class, or not? If `qwen3.6:27b` loops on 6 of 8 coder queries and `gemma3:27b` loops on 0 of 8, the conclusion is robust at N=1. If results are noisy at N=1, that itself is evidence — log it, recommend N=3 as a follow-up if needed. Don't budget for statistical significance testing on a research story whose primary purpose is "should we even ship a fix."

### Why filesystem and web tools are excluded

The bug under investigation is *synthesis from search*. Including `read_file`, `bash`, `web_fetch`, etc. broadens the tool-choice surface area in ways that confound the measurement. A model that calls `web_fetch` instead of `search_corpus` is exhibiting a different failure mode (corpus-trust vs. retrieval-discipline). Run with `search_corpus` only.

### Optional 4th cell: qwen3-coder:30b

`qwen3-coder:30b` is locally available and is a code-focused fine-tune of the Qwen-3 family. It does **not** fulfill the out-of-family disambiguation purpose and is therefore not in the spec'd matrix. If the maintainer wants an additional 16 runs (~30 minutes) to test "does Qwen-3's code fine-tune also exhibit the looping?", add it as cell 4. The recommendation logic in AC 6 still hinges on the three core cells; a 4th cell can refine but not invalidate the core conclusion.

### Coordination with my-agents repo

This story does not touch `agents/<name>.yaml`. The agent YAMLs are read read-only via the existing `scripts/local_rag.py` agent loader (`load_agent_persona`). No cross-repo coordination required.

If the recommendation is "per-agent prompt nudge," that follow-up PR will edit `my-agents` repo's agent YAMLs (extending `style:`) and is subject to the standard agent-config propagation flow: commit/push in `my-agents`, then either drop a doc in staging to trigger Ubuntu's git-pull-before-ingest, or restart the watcher. Flag this in the follow-up epic, not here.

### Public-mirror coordination

The query suite, runner, and report all land on public `main`. The runner uses already-public infrastructure. No private-only paths or personal data referenced. Single squash PR for the runner + suite; a second PR (or amendment) commits the report. Two PRs is cleaner here than one because the report is generated content with grading in it; reviewing it as its own diff is easier.

## Testing

**Test file location:** `tests/eval/test_agentic_loop_discipline.py` (new). Mirrors existing `tests/eval/` layout.

**Unit tests:**
- Query suite YAML validation: required fields, missing fields, malformed YAML, duplicate `id`s.
- Metric extraction from a synthetic `AgentLoopResult`: `redundant_retrievals` count, `expected_chunk_seen_at_iter` first-occurrence detection.
- Report rendering: aggregate table over a synthetic per-cell result set produces the documented columns.

**Integration tests:**
- Out of scope. The runner depends on a live Ollama instance and pulled models. The reproducer **is** the integration test, run manually by the maintainer.

**Manual validation:**
- The maintainer runs the full 48-cell matrix on their workstation. Grading happens at the CLI prompt per AC 4. The committed report is the validation artifact.
